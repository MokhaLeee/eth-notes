# RDMA 预研大纲（BSP）

站在 BSP 写 RoCEv2 预研时的学习提纲。每节先记下已经明确的结论，后面按这个结构继续补。

相关笔记：

- 报文与 Soft-RoCE demo：[rdma-test.md](rdma-test.md)，样例 [rdma-test.assets/demo/rdma_demo.c](rdma-test.assets/demo/rdma_demo.c)
- 无损网络：[sue.md](sue.md)

## 0. 先定的三个边界

1. **协议是 RoCEv2。** 以太网 + IPv4/IPv6 + UDP 目的端口 4791 + InfiniBand BTH。InfiniBand 专网和 iWARP 不在这次范围里。
2. **实现先分清两层，工作量差一个数量级。**
   - Soft-RoCE（`rdma_rxe`）：绑在现有 `net_device` 上。内核配置、rootfs、verbs 验收就能走通，用来打通接口。数据仍经过协议栈和这块 MAC 的普通 DMA，CPU 开销高，不能写成线速指标。
   - 硬件 RoCE：解析器把 UDP 4791 分流到独立 RoCE 引擎。引擎自己管 QP、PSN、重传，并对注册内存做 DMA。现有 XGMAC 的描述符 DMA 只服务普通收发包，硬件 RoCE 是另一块 IP 和另一套驱动。
3. **操作系统只写 Linux**（inbox 驱动 + `rdma-core`）。QNX `io-sock` 没有对等的 verbs 栈，若产品要双系统，单独列为风险。

性能目标要单独写死，例如背靠背在指定速率上 `ib_write_bw` 达到线速的多少、时延上限。没有数字时，Soft-RoCE 和硬件 RoCE 的结论会混在一起。

## 1. 背景与 BSP 交付物

BSP 交的是「板子上的 RDMA 能用」，包含：

- 内核配置片段、固件 / 设备树（若有）、rootfs 包列表
- 网卡与 RDMA 设备的绑定方式，以及开机自检命令
- 本机侧无损以太网要打开的开关，以及交换机侧必须满足的条件
- 一份用户操作说明：连通性、带宽验收、结果传到对端
- 指标、计数器，以及失败时先看什么

应用里的集合通信算法交给上层。BSP 保证设备和网络前提。

待补充：本板网口速率、目标带宽和时延、是否有 NVIDIA GPU。

## 2. 数据面和控制面

一帧 RoCEv2 的分层见 [rdma-test.md](rdma-test.md)。BSP 要分清每段谁处理：

| 段落 | 谁处理 |
| --- | --- |
| 以太网头、IP、UDP 4791 | MAC + 分流规则 |
| BTH / RETH / AETH、载荷、ICRC | RoCE 引擎或 `rxe` |
| QP 号、PSN、rkey、虚拟地址 | verbs 设备 |

### 2.1 UDP 4791

IANA 分配给 RoCEv2 的目的端口。每一帧数据的 UDP 目的端口都是 4791，载荷从 BTH 开始。

- 硬件 RoCE 靠这条规则把报文送进 RoCE 引擎。Soft-RoCE 由内核 `rxe` 在这条流上解析 BTH。
- 源端口由发送端按 QP 选择，用来给 ECMP 提供熵。同一条 QP 的源端口保持不变，避免乱序。
- 防火墙要放行两端之间的 UDP 4791。
- `rdma_listen` / demo 里的 `7471` 是建连服务号，不是 4791。

RoCEv1 用以太网类型 `0x8915`，只能在同一个二层里转发。RoCEv2 把同一套传输头放进 UDP/IP，路由器可以按普通 IP 转发。可靠传输仍由 RDMA 自己做（PSN、ACK、重传），所以外面用 UDP，只借用端口做分流。

### 2.2 建连和传数是两条路

- **建连**：`rdma_cm` 或业务自己的 TCP，交换 QP 号、`rkey`、虚拟地址、长度。demo 里 `rdma_create_id` 属于这一步；服务端在 `rdma_accept` 的 private data 里交出 `mem_info`。
- **传数**：用户态把工作请求交给网卡（或 `rxe`），完成事件从 CQ 回来。载荷不进 socket 接收队列。

RDMA WRITE 的语义：发起方写入对端已经注册好的内存，对端 CPU 不必参与这次拷贝。对端要事先 `ibv_reg_mr`，并把地址和 `rkey` 交给发起方。

### 2.3 地址空间

RDMA 打通的是网卡对一块已注册内存的 DMA。`malloc` 返回的仍是本进程虚拟地址，`memcpy` 拷贝的仍是本机页。两端指针不能混用。

要改远端一块缓冲，两端各自分配并注册，交换地址和 `rkey`，再用 RDMA WRITE / READ。进程里最终一定有一次 `ibv_post_send`（或通信库内部的同一次调用）。CPU 的 load/store 没有路径变成 UDP 4791 上的读请求。

用户不能把远端和本端当成同一块内存来操作。能接近「无感」的是另外两条路线，都不在这次 RoCE 驱动里：

- CXL：远端内存作为一个 NUMA 节点，load/store 能直接到达。
- 内核按页换入：页不在本地时用 RDMA 拉回一页。虚拟地址仍属于本进程，另一个进程的堆不会因此变成自己的堆。

待展开：注册内存的生命周期、`rkey` 失效、RC 上「先写数据再写标志」的可见性。

## 3. Linux 驱动怎么适配

### 3.1 两套驱动怎么配合

**网卡驱动（已有）** 继续负责链路、MAC、MTU、队列、NAPI、中断、ethtool。普通 TCP/UDP 仍走这条路径。

**RDMA 驱动（新增）** 向 `ib_core` 注册 `ib_device`，实现 PD、MR、CQ、QP、GID。RoCE 设备通过 netdev 绑定挂到同一块网卡上。GID 来自这块网卡上的 IP；IP、MTU、VLAN、链路状态变化时，GID 表要跟着更新。

协同点：

- 链路 up/down、MTU、MAC 地址
- IPv4/IPv6 地址增删（GID）
- VLAN、bonding、多网口时选哪一个 netdev
- 硬件 RoCE 的分流：UDP 4791 进 RoCE 引擎，其余仍进普通 DMA
- 中断可以共用 MSI-X，也可以拆开

差异：

- 网卡驱动管 skb 和协议栈；RDMA 驱动管 QP、CQ、MR
- 网卡缓冲由驱动分配；RDMA 缓冲由用户分配并注册，驱动钉住页面、建立地址翻译
- 网卡完成是 NAPI；RDMA 完成是 CQE，用户态 poll
- 网卡统计在 ethtool；RDMA 另有重传、PSN 错误、NAK 计数

### 3.2 内核与 rootfs

- `CONFIG_INFINIBAND`、`CONFIG_INFINIBAND_ADDR_TRANS`
- 第一阶段打开 `CONFIG_RDMA_RXE`；硬件方案再换成厂商 provider
- rootfs：`rdma-core`、`libibverbs`、`librdmacm`、`ibverbs-utils`、`perftest`，以及对应的 `-dev` 包
- `memlock` 要足够，否则 `ibv_reg_mr` 失败
- IOMMU/SMMU：注册内存要能 DMA

### 3.3 已经跑通的最小闭环

命令在 [rdma-test.md](rdma-test.md)：`rdma link add rxe0 type rxe netdev eno1`，然后 `rdma link show`、`ibv_devinfo`。demo 客户端在 `ibv_post_send` 里投递 `IBV_WR_RDMA_WRITE`，服务端只注册内存并轮询缓冲区。

硬件 RoCE 上，内核 RDMA 驱动的工作集中在开工前：钉页、建地址翻译和 `rkey`、创建 QP、填 GID、把门铃映射到用户态。每次 WRITE 由用户态投递，内核不再进数据路径。`rxe` 相反，每次写入仍进内核组 UDP 包，再交给网卡驱动。

待展开：本板若做硬件 RoCE，驱动分成 netdev 与 `ib_device` 的接口草案；GID 更新挂在哪个 netdev notifier 上。

## 4. 网络前提

RoCEv2 跑在以太网上。交换和拥塞不在网卡驱动里，但不写清的话，丢包重传会被当成驱动故障。机制见 [sue.md](sue.md)，标准名称是 DCQCN：

- **PFC**：按优先级暂停，避免缓存溢出丢包。写明本机优先级，以及交换机要做的 lossless priority。
- **ECN + DCQCN**：拥塞时降速。PFC 单独开时，暂停会冲到别的流量上，需要和 ECN 一起写。
- **CBFC**：若芯片或交换支持基于 credit 的流控，写进能力表，标出当前硅片是否具备。

板级参数：两端和交换的 MTU 一致（大包场景常用 9000）、DSCP 到优先级的映射、PFC 与普通 TCP 是否分优先级。

网络只转发帧，不理解「改内存」。交换机看到的是 UDP 4791。RC 的重传由两端网卡按 PSN 完成。丢包后功能仍在，带宽会掉下去。

背靠背可以先不接交换机，把驱动和 verbs 跑通。一带交换，PFC/ECN 就是必测项。

待展开：本机 `dcb` / ethtool 的具体开关，以及交换机侧的配置清单。

## 5. 用户怎么用

### 5.1 直接使用 verbs

参考 [rdma_demo.c](rdma-test.assets/demo/rdma_demo.c)。改远端内存时三层各自做的事：

**用户**

- 对端：`malloc`，`ibv_reg_mr`（打开 `IBV_ACCESS_REMOTE_WRITE`），建连时交出地址、`rkey`、长度。数据本身不用 `recv`。还要读这块内存时，约定一个标志，看到标志后再读。
- 本端：注册本地缓冲，取出对端地址和 `rkey`，`ibv_post_send` 投递 `IBV_WR_RDMA_WRITE`，轮询 CQ。

**驱动**

- 开工前：钉页、生成 `rkey`、创建 QP、填 GID、映射门铃。
- 每次写入：用户态写发送队列并敲门铃。本端网卡 DMA 读出数据并发 RoCEv2 包。对端网卡校验 `rkey`，DMA 写入，回 ACK。本端网卡收到 ACK 后产生 CQE。
- 硬件 RoCE 的 WRITE 载荷不进协议栈。`rxe` 仍进内核。

**网络**

- 转发 UDP 4791。写请求带 BTH（WRITE、目的 QP、PSN）和 RETH（对端虚拟地址、`rkey`、长度）。回程是 ACK。
- MTU 一致，这条优先级上尽量不丢包。

待展开：把 demo 的一次 WRITE 对照一帧 pcap，标出 BTH / RETH / ACK。

### 5.2 PyTorch 与 NCCL

PyTorch 用户写 `torch.distributed`，不写 verbs。GPU 用 NCCL，CPU 用编进 ibverbs 的 Gloo。两边先用 TCP 互相发现，张量再走 RoCEv2。

NCCL（NVIDIA Collective Communications Library）是用户态的 `libnccl.so`，不是内核驱动。它对外是集合操作和 rank 之间的 send/recv，搬运的是 GPU 缓冲。跨机器时，它自己注册显存、建 QP，并调用 verbs。没有 NVIDIA GPU 时这条路径不成立；CPU 上用 Gloo 或 MPI。

封装关系：

```text
PyTorch  dist.all_reduce / dist.send
  → NCCL   ncclAllReduce / ncclSend
    → IB 插件  regMr、isend，内部 IBV_WR_RDMA_WRITE
      → libibverbs
```

源码：[github.com/NVIDIA/nccl](https://github.com/NVIDIA/nccl)

- 对外接口：`src/enqueue.cc`（`ncclAllReduce`、`ncclSend`）
- 主机侧 proxy：`src/proxy.cc`
- verbs 封装：`src/transport/net_ib/p2p.cc`、`src/include/ibvwrap.h`、`src/misc/ibvwrap.cc`
- `libibverbs.so` 运行时 `dlopen`。没有 verbs 设备时可以退回 socket 插件，日志里就看不到 `NET/IB`。

NCCL 不用 `rdma_cm`。接收方把地址和 `rkey` 放进 FIFO 槽，发送方再 RDMA WRITE。QP 号和 GID 经 NCCL 自己的 TCP 引导连接交换。

地址怎么指定：

| 用途 | 由谁指定 |
| --- | --- |
| 进程互相发现 | `torchrun --master_addr --master_port`（TCP，例如 29500） |
| NCCL 引导连接用哪块网口 | `NCCL_SOCKET_IFNAME==eno1`（`=` 表示网口名完全一致） |
| 固定引导端口（纯 C、不用 torchrun 时） | `NCCL_COMM_ID=10.116.89.94:29500` |
| RDMA 设备 | `NCCL_IB_HCA==rxe0` |
| RoCE 用哪条 GID / IP | `NCCL_IB_GID_INDEX`，或按 IPv4 + RoCEv2 自动选 |
| 数据 UDP 目的端口 | 固定 4791，不能改 |

`master_addr` 应是 `NCCL_SOCKET_IFNAME` 那块网口上的 IP。日志里出现 `NET/IB` 和设备名，数据面才是 RDMA。

C 可以直接调 `ncclGetUniqueId`、`ncclCommInitRank`、`ncclAllReduce`、`ncclSend` / `ncclRecv`，缓冲区来自 `cudaMalloc`。Python 走 PyTorch，不直接 `import nccl`。

待展开：在有 GPU 的环境上用 `NCCL_DEBUG=INFO` 抓一份 `NET/IB` 日志，对照 `p2p.cc`。无 GPU 时改用 Gloo ibverbs 的编译开关和 `GLOO_DEVICE_TRANSPORT=IBVERBS`。

### 5.3 传到对端的操作顺序

1. 两端 IP 互通，`rdma link` 为 ACTIVE，`show_gids` 能看到要用的 GID，`memlock` 足够。
2. `ib_write_bw` 做带宽验收。这一步不过，不进入业务传输。
3. 按数据种类选路径：日志和小文件走现有 TCP；大块结果走已经跑通的 WRITE 样例、UCX，或 NFS over RDMA；多机训练走 NCCL / MPI。
4. `torch.save` 写到磁盘的文件不会自动改走 RDMA。张量要在 `destroy_process_group()` 之前 `dist.send`。

## 8. 工作量与风险

- **现在就能做**：`rxe` + `rdma-core` + perftest + 一份用户操作说明。用来验证接口、GID、权限和建连流程。
- **要硅片和交换一起才有意义**：硬件 RoCE、PFC/DCQCN、线速和时延。
- **风险**：把 Soft-RoCE 的带宽写成产品指标；交换机未配无损却要求线速；QNX 被默认为同一套步骤；上层期望显存直接注册（GPUDirect），本平台只有主机内存。

## 建议的推进顺序

1. 第 2、3 节：网卡驱动继续走协议栈，RDMA 设备挂在同一 netdev 上，第一阶段用 `rxe`。
2. 第 5 节：整理成 AI / 业务同事能照着做的操作说明。
3. 第 4、7 节：有 PFC/ECN 和验收数字之后，再写线速结论。
